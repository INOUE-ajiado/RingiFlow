RingiFlow 統合基本設計書

システムアーキテクチャ・モジュール・API仕様定義

1. システム概要

本システムは、申請者の社員IDを起点に「システム担当 → プロデューサー → 代表」の順に直線的なルートで進む稟議書承認フローシステムである。フロントエンドにAngular、バックエンドAPIにGo、データストアにCloud Firestore、認証にFirebase Authenticationを採用する。各承認段階でのステータス更新は、データの不整合を防ぐためGoバックエンドでのトランザクション処理にて厳密に行う。

【重要】トランザクション処理と状態管理の徹底

  • 整合性の担保： 承認ステータスの更新は、必ずGoバックエンド経由でFirestoreのトランザクションを用いて行い、複数人の同時操作やネットワーク遅延による競合（データ不整合）を防止する。
  • アジャイル開発方針（通知機能）： 現フェーズでは「メール等の通知機能」は要件外とし、コアとなる承認トランザクション・UI実装を優先する。通知連携は次以降のイテレーションにて検討・実装を行う。

2. システム構成・インフラアーキテクチャ

可用性と開発スピードを重視し、Firebaseを中心としたサーバーレス構成を採用する。

  • フロントエンド（Angular / Firebase Hosting）
    役割：ユーザーインターフェース（UI）の提供、Firebase Authを用いたログイン処理、およびバックエンドAPIへのリクエスト（申請・承認・一覧取得）。
  • バックエンドAPI（Go / Cloud Run）
    役割：認証トークン（JWT）の検証、権限チェック、およびFirestoreに対するトランザクション処理（ステータスの厳密な更新）。
  • データストレージ（Cloud Firestore）
    役割：稟議書のデータ、ユーザー情報、および承認履歴（監査ログ）の保存。
  • 認証（Firebase Authentication）
    役割：ユーザーの認証（ログイン・ログアウト）およびセッショントークン管理。

3. 業務フローと状態遷移

3.1 申請・承認フロー（正常系）

Step 1. ログイン: ユーザーはAngular画面から社員IDとパスワードを用いてFirebase Authでログインする。
Step 2. 新規申請: 申請者は稟議内容（タイトル、内容、金額等）を入力し、AngularからGoのバックエンドAPIへ申請リクエストを送信する。
Step 3. 申請処理（Go）: Go APIはリクエストとJWTを検証し、Firestoreへ新規稟議ドキュメントを作成。ステータスを「システム担当承認待ち（pending_system）」に設定する。
Step 4. システム担当承認: システム担当者がログインし、対象の稟議を「承認」する。Go APIがトランザクション処理によりステータスを「プロデューサー承認待ち（pending_producer）」へ更新する。
Step 5. プロデューサー承認: プロデューサーが「承認」する。同様にGoのトランザクション処理でステータスを「代表承認待ち（pending_ceo）」へ更新する。
Step 6. 最終決裁（代表）: 代表が「承認」する。Go APIがステータスを「決裁完了（approved）」に更新し、フローが完了する。

3.2 却下・差し戻しフロー（異常系）

Step 1. 却下/差し戻し操作: 任意の承認者（例：プロデューサー）が稟議内容に不備を見つけ、画面上から「却下」または「差し戻し」を実行する。
Step 2. 状態更新（Go）: Go APIはトランザクションを用いて、ステータスを「却下（rejected）」または「申請者へ差し戻し（returned）」に変更する。同時に監査ログ（コメント付き）を記録し処理を完了する。

3.3 状態遷移（ステートマシン）定義

システムの各状態（ステータス）と、実行可能なアクションの定義。

現在ステータス 操作可能権限 (Role) アクション 次ステータス
(新規作成) 申請者 (applicant) 申請 (Create) pending_system (システム担当待ち)
pending_system システム担当 (system_admin) 承認 (Approve) pending_producer (PD待ち)
pending_system システム担当 (system_admin) 差し戻し (Return) returned (差し戻し)
pending_producer プロデューサー (producer) 承認 (Approve) pending_ceo (代表待ち)
pending_producer プロデューサー (producer) 却下 (Reject) rejected (却下)
pending_ceo 代表 (ceo) 承認 (Approve) approved (決裁完了)

4. データベース設計 (Cloud Firestore)

NoSQLデータベースであるFirestoreの特性を活かし、データアクセス効率とセキュリティを考慮してコレクションとルールを設計する。

4.1 コレクション定義

users コレクション

フィールド名 型 説明
uid String Firebase AuthのUID（ドキュメントIDとして利用）。
employeeId String 社員ID（ログイン時などにも利用）。
name String 社員氏名。
role String 権限ロール（applicant, system_admin, producer, ceo）。

ringi_requests コレクション

フィールド名 型 説明
id String 稟議書の一意なID（自動生成）。
title String 稟議のタイトル。
content String 申請内容・理由等の詳細。
amount Number 金額（必要な場合）。
applicantId String 申請者の uid または employeeId。
status String 現在の状態（pending_system, ... approved 等）。
createdAt Timestamp 申請日時。
updatedAt Timestamp 最終更新日時。

audit_logs コレクション

フィールド名 型 説明
requestId String 対象となる稟議書のID。
action String 実行された操作（create, approve, reject, return）。
actorId String 操作を実行したユーザーのID。
comment String 承認、または却下・差し戻し時に入力されたコメント。
timestamp Timestamp 操作が行われた日時。

4.2 セキュリティルール (firestore.rules)

状態の不整合を防ぐため、クライアント（Angular）からの直接の書き込み（作成・更新・削除）は完全に禁止し、すべての状態変更はGoバックエンドを経由させる。

rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {
    // ユーザーは認証済みであれば読み取り可能。書き込みは禁止。
    match /users/{userId} {
      allow read: if request.auth != null;
      allow write: if false; // Go Admin SDK 経由のみ
    }
    // 稟議書データ
    match /ringi_requests/{requestId} {
      allow read: if request.auth != null;
      allow write: if false; // 承認・作成等はすべてGoAPI経由で行う
    }
    // 監査ログ
    match /audit_logs/{logId} {
      allow read: if request.auth != null;
      allow write: if false; // Go APIからのみ作成
    }
  }
}

4.3 複合インデックス要件

一覧画面でのクエリを成立させるため、以下の複合インデックスをFirebase Console上から設定する。

  • ringi_requests コレクション: status (昇順) + createdAt (降順)
  • ringi_requests コレクション: applicantId (昇順) + createdAt (降順)
  • audit_logs コレクション: requestId (昇順) + timestamp (降順)

5. バックエンドAPI設計 (Go)

Firestoreのセキュリティルールによる直接書き込みは制限し、状態変更を伴う操作は全てGo APIを経由させる。これにより、強固なトランザクションとビジネスロジックの集中管理を実現する。

5.1 エンドポイント構成とペイロード

# 主要なAPIエンドポイント構成
POST /api/v1/ringi                # 新規稟議の作成（申請）
GET  /api/v1/ringi                # 稟議一覧の取得（クエリパラメータで絞り込み）
GET  /api/v1/ringi/{id}           # 特定の稟議詳細と履歴（audit_logs）の取得
POST /api/v1/ringi/{id}/approve   # 稟議の承認
POST /api/v1/ringi/{id}/reject    # 稟議の却下・差し戻し

# リクエストBody例 (承認・却下時)
{
  "comment": "予算内であることを確認しました。進行お願いします。"
}

# レスポンスBody例 (200 OK)
{
  "success": true,
  "requestId": "r_123456789",
  "newStatus": "pending_producer",
  "updatedAt": "2024-05-10T10:00:00Z"
}

5.2 トランザクション処理フロー（承認API詳細）

1. リクエスト検証: HTTPヘッダーのBearerトークン（JWT）を検証し、ユーザーの uid と role を取得する。
2. トランザクション開始: client.RunTransaction を呼び出し、ブロックを開始する。
3. 対象ドキュメント取得: ringi_requests/{id} を読み込む。対象が存在しない、または既に「承認済み」の場合はエラー。
4. 権限・ステータス整合性チェック: 現在の status とアクセスユーザーの role が合致するかチェック。
5. 次ステータス決定: 進行ルートに従い、次ステータスまたは最終ステータス（approved）を決定する。
6. 更新書き込み: 対象ドキュメントの status および updatedAt をトランザクション内で更新する。
7. 監査ログ追加: 同じトランザクション内で、audit_logs コレクションに新規ドキュメントを作成する。
8. コミット: トランザクションを終了し、成功レスポンスを返す。

6. フロントエンド設計 (Angular)

Angular v16以上のStandalone Componentsをベースとしたモジュール/コンポーネント構成。

6.1 コンポーネント構成

コンポーネント名 役割・責務
AuthLoginComponent Firebase Authを用いた社員ID（メールアドレス等）とパスワードによるログイン画面。
RingiDashboardComponent 自分に関連する稟議一覧を表示するホーム画面。申請中/承認待ちなどのタブを表示。
RingiCreateComponent 新規稟議の入力フォーム画面。Reactive Formsを利用し、入力バリデーションを行う。
RingiDetailComponent 稟議の詳細内容および承認履歴（タイムライン）を表示。「承認」「却下」ボタンを動的に表示。
ActionDialogComponent 承認や却下ボタンを押した際に表示される、コメント入力用モーダル。

6.2 サービス（Service）構成

  • AuthService: Firebase Authのログイン状態を監視し、現在のユーザー情報とJWTトークンを取得する。
  • RingiService: HttpClientを用いてGoバックエンドAPIとの通信（申請、承認、一覧取得）を担う。
  • FirestoreService: AngularFireを利用し、Go APIを経由しなくてもよい「純粋な読み取り」を行う（例：一覧画面のリアルタイムアップデート）。
