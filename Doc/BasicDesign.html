RingiFlow 統合基本設計書

システムアーキテクチャ・モジュール・API仕様定義

1. システム概要

本システムは、申請者の社員IDを起点に「システム担当 → プロデューサー → 代表」の順に直線的なルートで進む稟議書承認フローシステムである。フロントエンドにAngular、バックエンドAPIにGo、データストアにCloud Firestore、認証にFirebase Authenticationを採用する。各承認段階でのステータス更新は、データの不整合を防ぐためGoバックエンドでのトランザクション処理にて厳密に行う。

【重要】トランザクション処理と状態管理の徹底

  • 整合性の担保： 承認ステータスの更新は、必ずGoバックエンド経由でFirestoreのトランザクションを用いて行い、複数人の同時操作やネットワーク遅延による競合（データ不整合）を防止する。
  • アジャイル開発方針（通知機能）： 現フェーズでは「メール等の通知機能」は要件外とし、コアとなる承認トランザクション・UI実装を優先する。通知連携は次以降のイテレーションにて検討・実装を行う。

2. システム構成・インフラアーキテクチャ

可用性と開発スピードを重視し、Firebaseを中心としたサーバーレス構成を採用する。

  • フロントエンド（Angular / Firebase Hosting）
    役割：ユーザーインターフェース（UI）の提供、Firebase Authを用いたログイン処理、およびバックエンドAPIへのリクエスト（申請・承認・一覧取得）。
  • バックエンドAPI（Go / Cloud Run）
    役割：認証トークン（JWT）の検証、権限チェック、およびFirestoreに対するトランザクション処理（ステータスの厳密な更新）。
  • データストレージ（Cloud Firestore）
    役割：稟議書のデータ、ユーザー情報、および承認履歴（監査ログ）の保存。
  • 認証（Firebase Authentication）
    役割：ユーザーの認証（ログイン・ログアウト）およびセッショントークン管理。

3. 業務フローと状態遷移

3.1 申請・承認フロー（正常系）

Step 1. ログイン: ユーザーはAngular画面から社員IDとパスワードを入力する。Angular側で社員IDを認証用メールアドレスへ変換し（3.4節）、Firebase Authでログインする。
Step 2. 新規申請: 申請者は稟議内容（タイトル、内容、金額等）を入力し、AngularからGoのバックエンドAPIへ申請リクエストを送信する。
Step 3. 申請処理（Go）: Go APIはリクエストとJWTを検証し、Firestoreへ新規稟議ドキュメントを作成。ステータスを「システム担当承認待ち（pending_system）」に設定する。
Step 4. システム担当承認: システム担当者がログインし、対象の稟議を「承認」する。Go APIがトランザクション処理によりステータスを「プロデューサー承認待ち（pending_producer）」へ更新する。
Step 5. プロデューサー承認: プロデューサーが「承認」する。同様にGoのトランザクション処理でステータスを「代表承認待ち（pending_ceo）」へ更新する。
Step 6. 最終決裁（代表）: 代表が「承認」する。Go APIがステータスを「決裁完了（approved）」に更新し、フローが完了する。

3.2 却下・差し戻しフロー（異常系）

各承認者は、自身が担当するステータスにおいて「承認」のほかに「差し戻し」「却下」を実行できる。両者は再申請の可否が異なるため、明確に区別して扱う。

  • 差し戻し（returned）： 記載内容に不備がある場合に用いる。申請者は内容を修正のうえ再申請が可能。再申請された稟議は pending_system から承認ルートをやり直す。
  • 却下（rejected）： 申請自体を認めない場合に用いる終端ステータス。再申請は不可であり、必要な場合は改めて新規申請として起票し直す。
Step 1. 却下/差し戻し操作: 任意の承認者（システム担当・プロデューサー・代表のいずれか）が稟議内容に不備を見つけ、画面上から「却下」または「差し戻し」を実行する。この際、理由コメントの入力を必須とする。
Step 2. 状態更新（Go）: Go APIはトランザクションを用いて、ステータスを「却下（rejected）」または「申請者へ差し戻し（returned）」に変更する。同時に監査ログ（コメント付き）を記録し処理を完了する。
Step 3. 修正・再申請（差し戻し時のみ）: returned の稟議は申請者本人のみが編集・再申請できる。Go APIはトランザクション内で申請者本人であることを検証したうえでステータスを pending_system へ戻し、監査ログに resubmit を記録する。

3.4 認証方式とアカウント発行方針

Firebase Authentication の「メール/パスワード」プロバイダを利用する。ただしユーザーが画面上で入力するのは社員IDとパスワードのみとし、Angular側で社員IDを固定ドメイン付きのメールアドレスへ変換したうえで signInWithEmailAndPassword に渡す。 

# 社員ID → 認証用メールアドレスの変換ルール
{社員ID}@ringiflow.ajiado.co.jp

# 例
E1234  →  E1234@ringiflow.ajiado.co.jp

自社ドメインのサブドメインを用いることで、実在する個人の業務用メールアドレスとの衝突・混同を回避する。将来的にMXレコードを設定すれば、パスワードリセットメール等の機能も利用可能となる。

【重要】アカウントのセルフ登録は行わない

  • 発行主体： アカウントの発行および権限ロール（role）の割り当ては、管理者が Firebase Console または Go の Admin SDK 経由でのみ実施する。フロントエンドにサインアップ画面は設けない。
  • ユーザー情報の整合： Firebase Auth のユーザー作成と同時に users コレクションのドキュメントを作成し、Firebase Auth の uid をドキュメントIDとして用いる。

4. データベース設計 (Cloud Firestore)

NoSQLデータベースであるFirestoreの特性を活かし、データアクセス効率とセキュリティを考慮してコレクションとルールを設計する。

4.1 コレクション定義

users コレクション

フィールド名 型 説明
uid String Firebase AuthのUID（ドキュメントIDとして利用）。
employeeId String 社員ID（ログイン時などにも利用）。
name String 社員氏名。
role String 権限ロール（applicant, system_admin, producer, ceo）。

ringi_requests コレクション

フィールド名 型 説明
id String 稟議書の一意なID（自動生成）。
title String 稟議のタイトル。
content String 申請内容・理由等の詳細。
amount Number 金額（必要な場合）。
applicantId String 申請者の uid（Firebase Auth UID）。JWTから直接取得でき改ざんが不可能なため、検索キーはこれに統一する。
applicantName String 申請者氏名（表示用）。Firestoreは結合クエリを行えないため、申請時に users からコピーして非正規化保持する。
applicantEmployeeId String 申請者の社員ID（表示用）。上記と同様の理由により非正規化保持する。
status String 現在の状態（pending_system, ... approved 等）。
createdAt Timestamp 申請日時。
updatedAt Timestamp 最終更新日時。

audit_logs コレクション

フィールド名 型 説明
requestId String 対象となる稟議書のID。
action String 実行された操作（create, approve, reject, return, resubmit）。
actorId String 操作を実行したユーザーの uid（JWTから取得）。
actorName String 操作者の氏名（表示用）。履歴タイムラインを1クエリで描画するため非正規化保持する。
comment String 承認、または却下・差し戻し時に入力されたコメント。
timestamp Timestamp 操作が行われた日時。

4.2 セキュリティルール (firestore.rules)

稟議データは金額を含む社内機密であり、また状態の不整合を防ぐ必要があるため、クライアント（Angular）からFirestoreへの直接アクセスは読み取り・書き込みともに全面禁止とする。データの取得・更新はすべてGoバックエンドAPIを経由させ、閲覧範囲の絞り込みと権限チェックをサーバー側で一元的に行う。

【重要】読み取りもGo API経由に一本化する

  • 機密性の担保： ルールを allow read: if request.auth != null とした場合、ログインした全社員が他者の稟議内容および金額を閲覧できてしまう。これを防ぐため読み取りも禁止し、「自身の申請」または「自身が承認すべき稟議」への絞り込みをGo API側で必ず実施する。
  • リアルタイム更新の不採用： 本方針によりクライアントSDKによるリアルタイム購読（onSnapshot）は利用しない。承認フローに秒単位の即時性は不要であり、一覧の更新は画面遷移時および手動更新時のAPI再取得で行う。
  • Admin SDK への非適用： Goバックエンドが用いる Admin SDK はセキュリティルールの評価対象外であるため、本ルールによる影響を受けない。
rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {

    // クライアントSDKからの直接アクセスは読み書きともに全面禁止する。
    // users / ringi_requests / audit_logs のすべてのデータ取得・更新は
    // Go バックエンドAPI（Admin SDK 経由）でのみ実施する。
    match /{document=**} {
      allow read, write: if false;
    }
  }
}

4.3 複合インデックス要件

一覧画面でのクエリを成立させるため、以下の複合インデックスをFirebase Console上から設定する。

  • ringi_requests コレクション: status (昇順) + createdAt (降順)
  • ringi_requests コレクション: applicantId (昇順) + createdAt (降順)
  • audit_logs コレクション: requestId (昇順) + timestamp (降順)

5. バックエンドAPI設計 (Go)

Firestoreのセキュリティルールによる直接書き込みは制限し、状態変更を伴う操作は全てGo APIを経由させる。これにより、強固なトランザクションとビジネスロジックの集中管理を実現する。

5.1 エンドポイント構成とペイロード

却下と差し戻しは再申請の可否が異なる別個の操作であるため、エンドポイントを分離する。これにより権限チェックをハンドラ単位で独立させられ、audit_logs.action の値とも1対1で対応する。

# 主要なAPIエンドポイント構成
GET  /api/v1/me                   # ログイン中ユーザーの氏名・社員ID・ロールの取得
POST /api/v1/ringi                # 新規稟議の作成（申請）
GET  /api/v1/ringi                # 稟議一覧の取得（クエリパラメータで絞り込み）
GET  /api/v1/ringi/{id}           # 特定の稟議詳細と履歴（audit_logs）の取得
POST /api/v1/ringi/{id}/approve   # 稟議の承認
POST /api/v1/ringi/{id}/return    # 稟議の差し戻し（申請者による再申請が可能）
POST /api/v1/ringi/{id}/reject    # 稟議の却下（終端・再申請は不可）
POST /api/v1/ringi/{id}/resubmit  # 差し戻された稟議の再申請（申請者本人のみ）

# リクエストBody例 (approve / return / reject)
#   comment は return・reject では必須、approve では任意とする
{
  "comment": "予算内であることを確認しました。進行お願いします。"
}

# レスポンスBody例 (200 OK)
{
  "success": true,
  "requestId": "r_123456789",
  "newStatus": "pending_producer",
  "updatedAt": "2024-05-10T10:00:00Z"
}

# エラーレスポンス例 (409 Conflict)
#   3.3節の状態遷移表に定義のない遷移、または権限が一致しない場合
{
  "success": false,
  "error": "invalid_state_transition",
  "message": "この稟議は既に他の承認者によって処理されています。"
}

GET /api/v1/me は、フロントエンドが操作ボタンの表示判定に用いる権限ロールを取得するためのエンドポイントである。ロールをクライアント側で保持・判断させず常にサーバーから取得させることで、権限の詐称を防ぐ。

GET /api/v1/ringi は、4.2節の方針に基づきアクセスユーザーの uid と role をもとに閲覧可能な範囲（自身が申請したもの、または自身が承認すべきもの）へ必ず絞り込んだうえで返却する。

5.2 トランザクション処理フロー（承認API詳細）

1. リクエスト検証: HTTPヘッダーのBearerトークン（JWT）を検証し、ユーザーの uid と role を取得する。
2. トランザクション開始: client.RunTransaction を呼び出し、ブロックを開始する。
3. 対象ドキュメント取得: ringi_requests/{id} を読み込む。対象が存在しない、または既に「承認済み」の場合はエラー。
4. 権限・ステータス整合性チェック: 現在の status とアクセスユーザーの role が合致するかチェック。
5. 次ステータス決定: 進行ルートに従い、次ステータスまたは最終ステータス（approved）を決定する。
6. 更新書き込み: 対象ドキュメントの status および updatedAt をトランザクション内で更新する。
7. 監査ログ追加: 同じトランザクション内で、audit_logs コレクションに新規ドキュメントを作成する。
8. コミット: トランザクションを終了し、成功レスポンスを返す。

差し戻し（return）、却下（reject）、再申請（resubmit）の各APIについても、上記と同一のトランザクション処理フローを適用する。Step 4の整合性チェックでは3.3節の状態遷移表を唯一の判定基準とし、表に定義のない遷移はすべて HTTP 409 で拒否する。なお resubmit については、ロールではなく操作者の uid が applicantId と一致することを検証条件とする。

6. フロントエンド設計 (Angular)

Angular v16以上のStandalone Componentsをベースとしたモジュール/コンポーネント構成。

6.1 コンポーネント構成

コンポーネント名 役割・責務
AuthLoginComponent 社員IDとパスワードによるログイン画面。入力された社員IDを認証用メールアドレスへ変換し（3.4節）、Firebase Authで認証する。
RingiDashboardComponent 自分に関連する稟議一覧を表示するホーム画面。申請中/承認待ちなどのタブを表示。
RingiCreateComponent 新規稟議の入力フォーム画面。Reactive Formsを利用し、入力バリデーションを行う。returned の稟議を申請者本人が修正・再申請する際の編集画面も兼ねる。
RingiDetailComponent 稟議の詳細内容および承認履歴（タイムライン）を表示。3.3節の状態遷移表に従い、現在のステータスとログインユーザーのロールに応じて「承認」「差し戻し」「却下」「再申請」ボタンを動的に表示する。
ActionDialogComponent 承認や却下ボタンを押した際に表示される、コメント入力用モーダル。

6.2 サービス（Service）構成

  • AuthService: Firebase Authのログイン状態を監視し、現在のユーザー情報とJWTトークンを取得する。3.4節の社員ID → 認証用メールアドレスの変換もここで行う。
  • RingiService: HttpClientを用いてGoバックエンドAPIとの通信（申請、承認、差し戻し、却下、再申請、一覧・詳細取得）を担う。読み取りを含むすべてのデータアクセスは本サービスに一本化する。

4.2節の方針によりクライアントからFirestoreへ直接アクセスすることはないため、読み取り専用サービス（FirestoreService）は設けない。クライアントにおけるFirebase SDKの利用はAuthenticationに限定されるため、ラッパーライブラリ（AngularFire）は導入せず、公式の firebase パッケージ（モジュラーSDK）を直接利用する。
